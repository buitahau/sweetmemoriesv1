# E2E tests

Python Playwright + pytest, one folder per feature (see the `e2e-from-user-stories` skill).

```
python3 -m venv .venv-e2e && .venv-e2e/bin/pip install playwright pytest pyyaml axe-playwright-python "psycopg[binary]"
.venv-e2e/bin/playwright install chromium
pnpm build
python3 .claude/skills/webapp-testing/scripts/with_server.py --server "pnpm start" --port 3000 -- \
  .venv-e2e/bin/pytest e2e/project-skeleton
```

`pnpm start` runs the built Cloudflare Worker with `wrangler dev` on port 3000. Set `E2E_BASE_URL` to target another local or dev URL (`e2e/dev-deploy` requires it, see below) (see [dev-environment](../docs/infra/dev-environment.md)). Never run against production.

`e2e/ci-pr-checks` has no browser: it checks the workflow file, reproduces failing inputs locally and reads branch protection with `gh api` (needs `gh` signed in). Run it with `.venv-e2e/bin/pytest e2e/ci-pr-checks`.

`e2e/dev-deploy` checks the deploy workflow, the real smoke script (against a throwaway local server), the deployed app at `E2E_BASE_URL` and, read-only, past `deploy-dev` runs via `gh`. Scenarios that need a real merge, a broken deploy or the Cloudflare dashboard are skipped as BLOCKED. Run it with `E2E_BASE_URL=<dev URL> .venv-e2e/bin/pytest e2e/dev-deploy -rs` (the dev URL is `sweetmemories-dev.<account>.workers.dev`, see [dev-environment](../docs/infra/dev-environment.md)). The deployed-app scenarios skip as BLOCKED when `E2E_BASE_URL` is unset or points at a local address, so local passes are not mistaken for dev evidence; set `E2E_ALLOW_LOCAL=1` to opt in to running them against a local `pnpm start`. Any other host that is not a `*.workers.dev` URL containing `sweetmemories-dev` fails the run (never production).

`e2e/dev-test-database` checks the repo, docs, deployed app and past run logs for the test database feature (no `DATABASE_URL` leak, `.env.example`, reset docs). Scenarios needing the Neon dashboard or Cloudflare credentials skip as BLOCKED. Run it with `E2E_BASE_URL=<dev URL> .venv-e2e/bin/pytest e2e/dev-test-database -rs` (same dev URL rules as `e2e/dev-deploy`).

## dev-test-database: optional ops checks

`e2e/dev-test-database` reads the Neon dev branch (GET requests only) when `NEON_API_KEY` and `NEON_PROJECT_ID` are set (add `NEON_DEV_ROLE`, the role name, for the least-privilege check), and the Worker secret when `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are set. Without them those scenarios skip as BLOCKED. A Neon API key can change the project even though this suite only reads, so use a project-scoped key and keep it out of the repo and CI logs. The ops steps themselves (task 01, task 02 secret) are done by a maintainer.

`e2e/google-sign-in` currently holds the checks for task 01 (workflow, `.env.example`, docs, env typing; static, no browser or server), task 02 (database access layer: static plus a `/api/health` request to `E2E_BASE_URL` or localhost:3000), task 03 (auth schema and first migration: static, plus the live check below) and task 04 (Better Auth route: static plus live `/api/auth/*` requests to `E2E_BASE_URL` or localhost:3000; the live cases skip as BLOCKED when the server has no auth config; to check the 503 path (`-k T04_V3`) run `pnpm start` without auth vars). Maintainer steps (Google Cloud, GitHub Environment, `wrangler secret list`) skip as BLOCKED. Task 06 adds `test_google_sign_in_task06_login_page_ui.py` (browser, US-google-sign-in-1.1 to 1.7: Login page idle state; needs `axe-playwright-python`; run with `with_server.py` as above). Task 07 adds `test_google_sign_in_task07_google_button_states.py` (browser, US-google-sign-in-2.1 to 2.4 and 4.1 to 4.4, plus the bfcache reset; cases needing a configured auth server skip as BLOCKED unless the probe returns 2xx with an accounts.google.com URL; set `E2E_SITE_URL` if the server's SITE_URL differs from `E2E_BASE_URL`). Task 08 adds `test_google_sign_in_task08_redirect_signed_in.py` (US-google-sign-in-5.1 and 5.2; 5.1 is BLOCKED unless `E2E_SESSION_COOKIE=name=value` carries a seeded session per ADR 0009). Task 10 adds `test_google_sign_in_task10_signed_in.py` (US-google-sign-in-3.3, 3.4, 5.1, 6.1, 6.2 and the `getSession` cookie-format check; 3.1 and 3.2 are skipped as manual on dev, ADR 0009) and `test_google_sign_in_task10_seed_helper.py` (unit checks of the seeding helper, no server). The seeded scenarios use `helpers.seed_signed_in_session`, which inserts a User, Account and Session and signs the cookie; they need `E2E_SEED_DATABASE_URL` (your own Neon developer branch, plus `E2E_SEED_NEON_ENDPOINT=<its ep-... endpoint id>`; the server talks Neon's SQL-over-HTTP protocol, so a plain local Postgres only works behind a local Neon HTTP proxy) and `E2E_BETTER_AUTH_SECRET` (or `BETTER_AUTH_SECRET`) equal to the server's secret, and skip as BLOCKED without them. The helper refuses a non-local `E2E_BASE_URL` and any Neon database whose endpoint id is not the allow-listed one (Neon hostnames never contain the branch name, so the allow-list is the only reliable guard against the dev or production database); run it against `pnpm start` with the same `DATABASE_URL` and secret. The task 03 live check (`test_T03_V1c`) runs `pnpm db:migrate` twice against an empty Neon developer branch: set `E2E_NEON_BRANCH_URL=<branch connection string>` and `E2E_ALLOW_MIGRATE=1` (never a production or shared database); without the URL it skips as BLOCKED. Run it with `.venv-e2e/bin/pytest e2e/google-sign-in -rs`.
